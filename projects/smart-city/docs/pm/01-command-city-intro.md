# 指挥城市介绍

## 一句话

**指挥城市**是 Urban Lens / 城景 面向运行指挥与运营决策的叙事：基于**城市场景平台**，把已接入的各类内容呈现在同一张图上，支撑「发现 → 研判 → 行动」。

## 产品关系

| 名称 | 角色 |
|------|------|
| **Urban Lens / 城景** | 产品品牌：城市场景平台 |
| **指挥城市** | 对运营者 / 指挥席的对外介绍口径 |
| **内容模块** | 挂在平台上的业务能力（自建微服务或外部贡献） |
| **smart-city** | 仓库与工程目录 |

城景**不承诺**自建「人们生活的方方面面」。生活与市政的广度，靠平台接入能力打开；当期只保证平台可用，并用少量种子内容证明路径。

## 要解决什么问题

1. **有数据、无空间共识**：说不清异常「在哪」。
2. **有地图、无一眼状态**：点位多，状态看不懂。
3. **想覆盖一切，范围失控**：把生活各域都做成自建系统，交付不可持续。

对策：先做稳平台与接入契约，再按需接入内容；指挥侧看到的是「当前已接入的城市内容」，而不是一张永远做不完的总清单。

## 平台主张（对外重点）

| 主张 | 说明 |
|------|------|
| 一张图 | 已接入对象落在同一城市场景 |
| 可接入 | 新内容按契约上图、出详情，不改无关模块 |
| 可替换 | 同一业务槽位可由自建或外部系统贡献 |
| 可指挥 | 运营者基于已接入内容做态势感知与研判 |

## 谁用、看什么

| 角色 | 主要诉求 | 说明 |
|------|----------|------|
| 城市运营 / 指挥席 | 全局态势、异常片区 | 取决于已接入的市政 / 出行等内容 |
| 内容提供方 | 稳定接入、可被发现 | 按 contribution / 路由契约挂入 |
| 物业 / 商户 / 市民 | 各域具体能力 | 仅在对应内容接入后可用 |

## 当前能力基线

| 能力 | 状态 | 说明 |
|------|------|------|
| 城市场景平台 | 已有 | 网关、场景聚合、静态场景 UI |
| 种子内容 | 已有 | traffic、parking、food、shopping、energy、environment |
| 种子深化 | 进行中 | parking / food / shopping 待与设计对齐 |
| 候选内容 | 未建 | community、property、leisure、checkin、ranking 等，按周期择优接入 |

近期**非目标**：全能生活操作系统、数字孪生仿真、闭环自控、替代专业 SCADA / GIS。详见 [愿景](../design/01-vision.md)。

## 成功标准（指挥城市视角）

1. 说得清：对外介绍以「平台 + 已接入内容」为准，不把候选域说成已具备。
2. 接得上：新内容可按契约进入场景聚合。
3. 看得懂：运营者能在已接入内容上快速定位异常片区。
4. 演得动：用种子内容即可完成端到端演示，不依赖打卡/榜单等候选域。

## 对外介绍建议结构（路演 / 评审）

1. **问题**：城市信息散、看不见、想做大又做不完。
2. **主张**：先搭城市场景平台，再接入各种各样的内容。
3. **演示**：场景加载 → 点选种子内容看状态 → 说明如何再挂一个新模块。
4. **边界**：平台不包办全部生活业务；候选域按节奏接入或由外部贡献。
5. **路线**：见 [项目周期编排](./02-project-cycle.md)。
