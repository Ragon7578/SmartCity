# 指挥城市介绍

## 一句话

**指挥城市**是 Urban Lens / 城景 面向城市运行指挥与运营决策的产品叙事：在同一张可互动城市场景上，先看见城市对象，再看见运行与生活数据，支撑「发现 → 研判 → 行动」。

## 产品关系

| 名称 | 角色 |
|------|------|
| **Urban Lens / 城景** | 产品品牌与工程代号 |
| **指挥城市** | 对运营者、指挥席、物业与商户运营的对外介绍口径 |
| **smart-city** | 仓库与微服务工程目录 |

对市民侧，同一套城景能力可表达为生活服务与打卡闭环；对指挥侧，则强调全局态势、异常片区与可运营指标。两侧共用场景聚合与领域微服务，不拆成两套系统。

## 要解决什么问题

传统智慧城市材料常见三类断层：

1. **有数据、无空间共识**：表格与大屏割裂，异常说不清「在哪」。
2. **有地图、无一眼状态**：点位很多，颜色与动效无法先于说明文字传达问题。
3. **有模块、无生活与运营闭环**：交通、停车、餐饮、购物各自为政，指挥与市民路径都断。

指挥城市把市政运行与市民生活放进同一底图：出行、居住、消费、互动、运营同一套空间对象模型，模块可独立扩展。

## 谁用、看什么

| 角色 | 主要诉求 | 场景示例 |
|------|----------|----------|
| 城市运营 / 指挥席 | 全局热力、异常片区、设施健康 | 5 秒内从场景识别告警片区 |
| 物业人员 | 小区空间、工单与设施 | 片区定位 → 工单 / 巡检（规划域） |
| 商户运营 | 客流、榜单、活动点 | 商场周边停车与餐饮联动 |
| 市民 / 游客 | 停车、美食、购物、打卡 | 「附近停车 → 用餐 → 打卡」最小闭环 |

## 能力分层（对外介绍口径）

```
城市底图（区 / 街道 / 小区 / 商圈）
    ├── 出行层：交通、停车
    ├── 居住层：小区、物业（规划）
    ├── 消费层：餐饮、购物、玩乐（玩乐规划）
    ├── 互动层：打卡、足迹（规划）
    ├── 市政感知：能源、环境
    └── 运营层：排行榜、热度、活动（规划）
```

工程落地为 Spring Cloud 微服务 + 网关静态城市场景；场景由 `city-scene` 聚合各模块可视化贡献。详见 [架构](../design/02-architecture.md) 与 [业务域总览](../design/07-city-domain-overview.md)。

## 当前能力基线（介绍时可如实表述）

| 能力 | 状态 | 说明 |
|------|------|------|
| 城市场景可视化 | 已有 | 网关 `:8080` 静态场景 + 场景聚合 API |
| 交通 / 停车 / 餐饮 / 购物 | 已有 | 停车、餐饮、购物待深化 |
| 能源 / 环境 | 已有 | 市政感知点位与指标 |
| 小区 / 物业 / 玩乐 / 打卡 / 排行榜 | 规划 | 设计文档已具备，工程待建 |

近期**非目标**（介绍时需划清边界）：完整物理级数字孪生仿真、闭环自动控制替人工决策、替代专业 SCADA / GIS 账本地位。详见 [愿景](../design/01-vision.md)。

## 成功标准（指挥城市视角）

1. 运营者能在场景上快速定位异常片区，而不是先翻报表。
2. 市民侧最小生活闭环可演示（停车 → 用餐 → 打卡，打卡上线后闭环完整）。
3. 榜单与热度可解释、可配置（排行榜域上线后）。
4. 新业务域按微服务模板接入，不拖垮既有模块。

## 对外介绍建议结构（路演 / 评审）

1. **问题**：城市运行与生活信息看不见、看不全、看不联。
2. **主张**：先可视化城市事物，再可视化展示数据。
3. **演示**：打开城市场景 → 点选对象看状态 → 跨模块联动（如商场 → 附近停车 → 周边餐饮）。
4. **边界**：指挥辅助与态势感知，不做全自动闭环控制。
5. **路线**：见 [项目周期编排](./02-project-cycle.md)。
