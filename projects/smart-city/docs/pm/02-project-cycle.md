# 项目周期编排

本文定义 Urban Lens / 城景（指挥城市）的交付阶段、里程碑与模块优先级。技术细节以 `docs/design/` 为准；本文只排**做什么、何时做、依赖与风险**。

## 编排原则

1. **先看得见，再看得懂**：场景与空间对象优先于报表与复杂运营配置。
2. **先打通已有，再扩建规划域**：深化 parking / food / shopping，再开 community 等新服务。
3. **一域一服务**：新业务按微服务模板扩展，聚合层与网关同步接入。
4. **可演示优先**：每个阶段结束须有可演示路径，而不是仅有设计或半拉子 API。
5. **边界清晰**：不做数字孪生仿真与闭环自控；人工决策为主。

## 现状基线（周期起点）

| 类别 | 内容 |
|------|------|
| 平台 | Eureka、Gateway、city-scene、静态城市场景 UI |
| 已有业务 | traffic、parking、food、shopping、energy、environment |
| 待深化 | parking、food、shopping（设计已扩展，工程能力未齐） |
| 规划业务 | community、property、leisure、checkin、ranking |
| 文档 | `docs/design/` 01–13 已齐；`docs/pm/` 负责介绍与周期 |

版本口径：后端 Maven `0.1.0-SNAPSHOT`。

## 阶段总览

```
P0 基线稳固 ──► P1 出行与消费深化 ──► P2 居住与物业 ──► P3 互动运营闭环 ──► P4 指挥体验打磨
     已有平台            深化三域              新服务              打卡+榜单           态势与可用性
```

| 阶段 | 主题 | 退出条件（DoD） |
|------|------|-----------------|
| **P0** | 基线稳固 | 一键启停稳定；场景可加载；核心服务健康检查通过；介绍口径与周期文档可用 |
| **P1** | 出行与消费深化 | 停车 / 餐饮 / 购物在场景上状态可读、详情可点、与场景聚合一致 |
| **P2** | 居住与物业 | community + property 服务可注册；小区边界与工单/设施可在场景呈现 |
| **P3** | 互动运营闭环 | checkin + ranking + leisure 可演示；「停车→用餐→打卡」闭环可走通 |
| **P4** | 指挥体验打磨 | 运营者异常片区识别路径清晰；关键指标与告警表达统一；文档与演示脚本同步 |

阶段之间允许部分并行（例如 P1 深化与 P2 设计细化），但**新服务合入主演示路径**须满足上表退出条件。

## 里程碑

| ID | 名称 | 阶段 | 交付物 |
|----|------|------|--------|
| M0 | 指挥城市口径就绪 | P0 | 介绍文档、周期文档、README 入口 |
| M1 | 场景基线可演示 | P0 | start-all 稳定；UI + `/api/v1/city/scene` 可用 |
| M2 | 停车深化可演示 | P1 | 车场/余位/状态在场景与详情一致 |
| M3 | 餐饮·购物深化可演示 | P1 | 门店状态、客流/排队等关键指标可展示 |
| M4 | 小区空间上图 | P2 | community 贡献边界与楼栋/出入口点位 |
| M5 | 物业运行上图 | P2 | property 工单/设施状态可点选 |
| M6 | 打卡上线 | P3 | checkin 点位、足迹写入与展示 |
| M7 | 榜单上线 | P3 | ranking 可配置周期与快照查询 |
| M8 | 生活闭环演示 | P3 | 脚本化演示：商场/餐饮 → 停车 → 打卡 → 榜单 |
| M9 | 指挥席最小可用 | P4 | 异常/告警视觉规范 + 运营者 5 秒识别路径说明 |

## 模块优先级（执行序）

| 优先级 | 模块 | 阶段 | 理由 |
|--------|------|------|------|
| P0 | platform（registry/gateway/city-scene/web） | P0 | 一切演示的承载体 |
| P1-a | parking | P1 | 出行刚需，闭环入口 |
| P1-b | food、shopping | P1 | 消费主路径，设计已先行 |
| P1-c | traffic、energy、environment | P1 | 保持可用；仅修阻塞与聚合一致性，不大改 |
| P2-a | community | P2 | 居住空间是物业与局部运营的底图 |
| P2-b | property | P2 | 依赖小区空间对象 |
| P3-a | checkin | P3 | 闭环最后一跳 |
| P3-b | ranking | P3 | 依赖消费/打卡数据因子 |
| P3-c | leisure | P3 | 可与 food 场景协同，略后于打卡主路径 |

## 每阶段工作包（编排清单）

### P0 — 基线稳固

- [x] 设计文档 01–13 齐备（历史交付）
- [x] 指挥城市介绍与本周期文档（本目录）
- [ ] 启停脚本与 README 试用路径复核
- [ ] 场景聚合与各已有模块 contribution 冒烟
- [ ] 明确演示账号/本地启动检查清单（可附 README）

### P1 — 出行与消费深化

- [ ] parking：余位、状态、引导相关展示与 API 对齐设计
- [ ] food：排队/门店状态等关键展示
- [ ] shopping：客流等关键展示
- [ ] city-scene / gateway / web 同步
- [ ] 回归：`mvn test` + 场景点选路径

### P2 — 居住与物业

- [ ] 新建 `smartcity-community`、`smartcity-property`（模板对齐现有模块）
- [ ] 注册、网关路由、scene contribution
- [ ] 小区边界与物业对象上图
- [ ] 设计偏差记录回写 `docs/design/09`

### P3 — 互动运营闭环

- [ ] `smartcity-checkin`、`smartcity-ranking`、（可选同期）`smartcity-leisure`
- [ ] 打卡写入与展示；榜单周期与快照
- [ ] 端到端演示脚本（指挥城市介绍中的闭环）
- [ ] 成功标准对照 [愿景](../design/01-vision.md)

### P4 — 指挥体验打磨

- [ ] 统一 status 视觉（online / warning / critical / offline）
- [ ] 异常片区识别路径（运营者视角说明 + UI 强化）
- [ ] 介绍文档与演示脚本终检
- [ ] 下一轮周期（规模化数据、权限、多租户等）另开编排，不混入本轮

## 依赖关系

```
platform (P0)
    └── parking / food / shopping 深化 (P1)
            ├── community (P2)
            │       └── property (P2)
            ├── checkin (P3)  ← 建议在消费深化后
            │       └── ranking (P3)  ← 因子依赖门店/打卡
            └── leisure (P3)  ← 可与 food 并行，勿阻塞打卡主路径
```

traffic / energy / environment：不阻塞 P1–P3 主路径；仅在聚合或演示损坏时插队修复。

## 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 深化与新域并行导致场景回归失败 | 演示不可用 | 每里程碑强制 scene 冒烟；合入前跑 `mvn test` |
| 规划域范围膨胀 | 周期失控 | 严格按优先级表；leisure 可降级为 P3 末或下一轮 |
| 介绍口径与实现不一致 | 干系人预期失控 | 介绍文档只写基线事实；规划能力标注「规划」 |
| 聚合层成为瓶颈 | 多模块联调慢 | contribution 契约保持稳定；新模块先最小字段上图 |
| 把指挥城市做成自动闭环控制 | 范围失控 | 坚守愿景非目标；告警到人，决策留人 |

## 协作与变更

| 事项 | Owner 口径 |
|------|------------|
| 介绍文档、周期优先级、里程碑 DoD | 项目经理（本文档负责人） |
| 领域模型与接口设计 | 设计文档维护者 / 研发 |
| 服务实现与测试 | 对应模块研发 |
| 可视化与交互 | web / 场景相关研发 |

变更规则：

1. **调整模块优先级或砍范围**：先改本文，再改排期。
2. **调整接口或领域对象**：先改 `docs/design/`，实现跟随。
3. **对外介绍话术变更**：先改 [01 指挥城市介绍](./01-command-city-intro.md)。
